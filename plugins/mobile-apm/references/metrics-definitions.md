# 指标口径定义

> **为什么需要这份文件**：性能优化中最常见的错误不是"优化方法不对"，而是
> **拿两个口径不同的数字做对比**（比如拿模拟器 debug 构建的数据对比真机 release 构建），
> 然后得出完全错误的结论。所有报告必须声明口径。

---

## 0. 通用纪律

### 0.1 用中位数和分位数，不要用平均值

平均值会被长尾拖偏。行业标准是看 **pct50（中位）**，配合 **pct90 / pct95** 看长尾。

| 指标 | 看什么 | 为什么 |
|---|---|---|
| 启动耗时 | pct50 + pct90 | pct50 反映典型体验，pct90 反映差体验用户 |
| 帧耗时 | **pct95** | 卡顿是长尾事件，平均值看不出卡顿 |
| 内存 | peak + avg | peak 决定是否被杀 |

### 0.2 必须声明的测量上下文

任何性能数字，报告时必须同时给出：

- **构建类型**：release / debug（⚠️ debug 有大量额外开销，两者不可比）
- **设备**：具体机型 + 系统版本 + 是否真机（⚠️ 模拟器性能特征与真机完全不同）
- **commit sha**
- **测量命令**（可复现）
- **样本量**（几次运行）与**方差**

### 0.3 测量噪声

**至少测 5 次，保留全部样本。** 先运行 `apm_diagnose.py`；如果 CV > 30%、
检出疑似多峰或样本不可计算，说明**测量方法本身不可靠，必须先稳定测量，再谈优化**。
不要在有噪声的数据上做 A/B 判断——你分不清是优化生效了还是噪声。

### 0.4 控制变量（借自抖音启动优化的实践）

- 关闭 iCloud、不登录 AppleID、飞行模式
- 设备降温（发热会降频，直接污染数据）
- 重启设备后静置一段时间
- 使用 MFI 认证数据线
- 稳定性排序（iPhone 8 最好，其次 iPhone X，iPhone 6 很差——老旧设备波动大）

### 0.5 标准工件与诊断

标准测量 profile 生成的 `metrics.json` 除 `context` + `metrics` 外，还应保留
逐次 `observations`：

- `firstFrameMs`：本次启动终点；
- `premainMs` 与 `premainSource`：取不到时为 `null`/unavailable，不写 0；
- `stages[]`：每个阶段的 `sinceMs` 与 `deltaMs`；
- `rawLog`：对应的原始日志路径。

`apm_diagnose.py` 读取这些数据后输出 CV、疑似多簇、分段 CV、可疑变量相关性
和判据建议。**相关性只用于提出控制实验假设，不能自动分层或校正。**

## 1. 启动耗时

### 1.1 三种启动的定义

| 类型 | 定义 | 典型目标 |
|---|---|---|
| **冷启动** | 进程不存在，从头创建 | 最受关注，优化主战场 |
| **温启动** | 进程被系统回收但部分内存/缓存仍在 | 介于两者之间 |
| **热启动** | 进程仍在后台，仅切回前台 | 通常很快，除非后台被挂起 |

> ⚠️ 提高热启动在总启动中的占比本身是一种"优化手段"（抖音用 Background Fetch 实现）。
> 但它把成本转移到了后台，需评估副作用。

### 1.2 起止点口径（iOS）

**起点**：`进程创建`（用 `sysctl` 系统调用取时间戳，这是最客观的起点）

**终点**：iOS `firstFrame` —— 在 `onAppear` 后延迟一个 runloop，逼近第一个
`CA::Transaction::commit`。不要用直接 `onAppear` 或 `applicationDidBecomeActive`
替代；不同终点不可比。

> ⚠️ **口径必须全链路一致**。如果基线用 `viewDidAppear`、验证时用 `applicationDidBecomeActive`，
> 那测出来的差异里混了口径差异，结论无效。

### 1.3 分段（诊断用）

```
进程创建 → 最早 +load → didFinishLaunching 开始 → 首屏首次绘制完成
                                                  → 业务初始化完成
```

RN 应用还需插入：`ReactInstanceManager 初始化` → `bundle 加载/解析`
→ `Hermes 字节码加载` → `根组件挂载`

> ⚠️ **观察者选型有坑**：iOS 13+ 用 `kCFRunLoopBeforeTimers` 回调更准；
> iOS 13 以下用 `CFRunLoopPerformBlock` 注入 block 更准。

### 1.4 度量手段的硬限制

| 手段 | 限制 |
|---|---|
| MetricKit | **24 小时延迟**；需用户开启共享；**模拟器不支持** |
| XCTest `XCTApplicationLaunchMetric` | **baseline 按设备型号绑定，换机即失效**；模拟器数据不准 |
| Sentry App Start | 只有总量，**无 RN 内部分段** |

## 2. 渲染 / 卡顿

### 2.1 帧耗时（Android 侧术语最严谨）

| 指标 | 含义 |
|---|---|
| `frameDurationCpuMs` | 单帧 CPU 耗时，看 p50/p90/p95/p99 |
| **`frameOverrunMs`** | **错过 deadline 的量。负值=准时，正值=错过了多少** |

👉 **核心指标是 p95 `frameOverrunMs`** —— 它回答"滚动中最坏的那一帧有多糟"。

### 2.2 卡顿判定

- **Android JankStats**：`jankHeuristicMultiplier` 默认 2（即帧耗时超过刷新率 2 倍判为 jank）。
  它比原始 `FrameMetrics` 强在能判定"用户实际感知的卡顿"
- **iOS hitch**：MetricKit `scrollHitchTimeRatio`，单位 ms/s（每秒卡顿毫秒数）
- **鸿蒙 SCROLL_JANK**：**单帧 > 50ms 即上报**（约 3 个 60Hz 帧）

### 2.3 RN 专属：必须分离观测两种 FPS

这是 RN 卡顿归因的**关键**：

| 指标 | 含义 | 瓶颈指向 |
|---|---|---|
| **JS FPS** | JS 线程处理能力 | 瓶颈在 JS 逻辑（重计算、频繁 setState） |
| **UI FPS** | 原生渲染线程 | 瓶颈在原生渲染/布局 |

**只测一个数是没有诊断价值的** —— 3 FPS 的 JS 线程 + 60 FPS 的 UI 线程，
和 60 FPS 的 JS + 3 FPS 的 UI，是完全不同的问题，修法完全相反。

### 2.4 页面可交互指标

| 指标 | 含义 |
|---|---|
| **TTID** (Time to Initial Display) | 首帧绘制完成（自动结束） |
| **TTFD** (Time to Full Display) | 完整可交互（**需手动调 `Sentry.reportFullyDisplayed()`**） |

> ⚠️ `enableTimeToFullDisplayTracing` 默认关闭，需显式开启。
> 若 30s 内未调用 report 会标记 `deadline_exceeded`。

## 3. 白屏

### 3.1 定义

白屏 = 页面已进入但**未渲染出有效内容**，且持续时间超过用户可感知阈值。

**判定阈值建议**：> 1s 即需关注，> 2s 视为故障。

### 3.2 判定方法（三选一或组合）

| 方法 | 原理 | 误报风险 |
|---|---|---|
| 分段打点 + 超时 | 首屏渲染点未触发即告警 | 无（但需埋点） |
| 截图/像素比对 | 抓 RootView 快照，判断是否纯色 | 深色模式、纯色设计的页面会误判 |
| View 树检测 | 根节点无子节点 | 页面本就为空时会误判 |

> **结论**：2026 年**没有单一可用的 RN FCP API**。必须组合使用，
> 并配合 Native Splash / 骨架屏遮蔽（把白屏等待变成品牌感知）。

## 4. 内存

### 4.1 指标

| 指标 | 平台 | 含义 |
|---|---|---|
| `peakMemoryUsage` | iOS | 峰值内存 |
| `averageSuspendedMemory` | iOS | 后台挂起时平均内存 |
| **PSS** | Android/鸿蒙 | 实际物理占用（含共享库按比例分摊）—— **判断 OOM 用这个** |
| RSS | 通用 | 常驻集，偏大 |
| JS Heap | RN | Hermes 堆使用量 |

> ⚠️ **PSS 才是决定是否被系统杀的依据**，不是 RSS。鸿蒙用 `hidebug` 取 PSS/RSS。

### 4.2 iOS 后台内存红线

官方建议：**后台内存压到 50MB 以下**，可显著降低 jetsam 回收概率。

### 4.3 FOOM / OOM 定义

| 术语 | 平台 | 定义 |
|---|---|---|
| **FOOM** | iOS | Front-most Out Of Memory —— 前台时被系统因内存压力杀死 |
| **jetsam** | iOS | 系统内存回收机制主动杀进程 |
| **OOM** | Android | 内存超限被杀 |

⚠️ **这类"崩溃"不会出现在崩溃报告里**（没有信号、没有异常），
表现为"用户说 App 莫名其妙退出了，但崩溃平台没有记录"。

**归因必须自建**：内存水位曲线 + `MXAppExitMetric` / `ApplicationExitInfo` 交叉验证。
详见 `stack-selection.md` §5。

## 5. 崩溃

### 5.1 核心指标

| 指标 | 定义 |
|---|---|
| **Crash-Free Users** | 未发生崩溃的用户数 / 总用户数 —— **比 Crash-Free Sessions 更贴近体感** |
| **Crash-Free Sessions** | 未崩溃会话 / 总会话 |
| 崩溃率 | 崩溃次数 / 启动次数 |

### 5.2 聚类与归因优先级

崩溃必须**先聚类再修**，否则会在长尾上浪费全部时间。

**聚类键（按优先级）**：
1. **鸿蒙**：HiAppEvent `params.uuid`（故障特征码，官方提供）
2. **iOS**：符号化后的崩溃栈 top frame + 异常类型
3. **RN**：JS 错误 message + 栈指纹

**排序依据**：`影响用户数 × 单次影响严重度`。**优先修 top 3**，
不要因为某个崩溃看起来"简单"就先修它。

### 5.3 每个崩溃必须回答的问题

1. 崩溃在**谁的代码**里（业务 / 三方 SDK / 系统）？
2. 触发的**前置条件**是什么（特定机型？特定系统版本？特定操作序列？）
3. 是**必现**还是**概率性**？概率性的话分布特征是什么？
4. 有没有**同类崩溃的历史记录**（是不是回归）？
