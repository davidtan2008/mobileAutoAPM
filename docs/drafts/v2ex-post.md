## 正文

```
先说结论：这个项目最有用的功能，是**劝退**。

我给自己的项目定了「冷启动 ≤200ms」，Agent 优化了三轮，
280ms → 279ms，p=0.605。它没宣布失败收工，
而是先造了个最小对照组：首页内容换成 Text("x")，其余全保留。

  目标 200ms  <  空壳 App 地板 210ms
  → blocked_by_control_floor
  → 停止局部优化，升级架构决策

这个"失败"比任何优化成果都值钱——它避免了在物理上不可能的方向上继续投入。

## 痛点

崩溃上报工具（Sentry / Bugly / Firebase）解决的是"线上出事了怎么看"。

它们不回答三个问题，而这些恰恰是性能优化的全部难点：

1. 这个目标到底可达吗？空壳 App 的启动地板就在那儿
2. 这次改动真的有效果吗？方差常常比优化幅度还大
3. 为什么突然变慢了？同一个 App 里方差源能有两倍差

**大多数"性能优化"失败，不是因为改错了，而是因为无法判断有没有改对。**

——

## 做法

核心是五条铁律，写进每个技能里，Agent 违反任何一条就算任务失败：

1. 无基线不优化    2. 单变量    3. 必须复测
4. 绝不伪造        5. 结论带来源

第 4 条是专门给 LLM 设的。**LLM 做性能优化最常见的失败模式，
是编一个看起来合理的数字，然后基于它改一堆代码。**

这条被真实触发过：一个 iOS 项目冷启动数据是双峰分布——
快的一簇 235ms，慢的一簇 500ms。挑两个快的就能报出"优化了 11%"。

工具的做法是：方差超阈值就整轮拒绝，并明确告诉你"本次无法判定"，
而不是换个口径重测到好看为止。

架构上有个简单原则：**确定性的计算交给脚本，判断留给 Agent。**
解析 sourcemap、算 CV、跑置换检验全是零依赖的确定性脚本；
改哪里、要不要问人才交给模型。11 个脚本全部只用 Python 标准库。
```
