# 重构方案（草案）

> 状态：**草案**，待市场调研结论回来后定稿。
> 2026-09-25

---

## 一、新定位

**一句话**：让移动端项目**对 AI 友好**，并让 AI **自主**把移动端性能与稳定性问题解决掉。

**两根支柱，共享底层**：

```
              mobileAutoAPM
      AI 原生的移动工程平台
    ┌─────────────────────────────────┐
    │  支柱 A          支柱 B          │
    │  项目 AI 化改造    APM 自主闭环     │
    │                                 │
    │  遗留项目 →       发现 → 定位 →    │
    │  AI 可读可改可验证  修复 → 验证     │
    └─────────────────────────────────┘
         共享：工具层 · 知识层 · 适配层
```

**为什么是两根而不是两个项目**：

> **支柱 A 的产物，正是支柱 B 能自主工作的前提。**
> 一个没有测试、构建命令不明、目录无边界、缺 context 文件的项目，
> agent 既无法理解它，也**无法验证自己的任何改动** ——
> 此时谈"自主优化性能"是空话。

支柱 A 是地基，支柱 B 是上层建筑。两者共享同一套工具与知识。

## 二、支柱 A：项目 AI 化改造

### 可判定的标准（不是口号）

「AI 友好」拆成 5 个维度，每项都能在仓库里实际查证：

| 维度 | 核心问题 | 不达标的后果 |
|---|---|---|
| **文档层** | Agent 能否在入口处知道这是什么、怎么跑？ | 每次新会话重新摸索 |
| **可验证性** | Agent 能否验证自己的改动？ | **最致命** —— 只能靠猜 |
| **一键构建** | 一条命令能否跑通？ | 猜错构建方式浪费整轮 |
| **可导航性** | 结构是否有边界、有命名约定？ | 改动误伤、token 浪费 |
| **移动端特化** | 签名/设备依赖/慢构建是否已解？ | 只能停在模拟器 |

**评分工具**：`plugins/mobile-apm/scripts/ai_readiness.py`
已在本项目与一个真实遗留 iOS 项目上跑通（见 §五 实测）。

### 改造工作流

```
扫描 → 评分报告 → 生成改造项 → 执行 → 复扫验证
```

产出物（按项目实际情况生成，**不是套模板**）：

- `AGENTS.md` —— 跨 agent 的项目约定（构建/测试命令、目录、坑与禁区）
- `ARCHITECTURE.md` —— 模块划分、依赖方向
- 最小 CI —— 构建 + 测试
- lint / format 配置
- `.gitignore` 补全
- 必要时：测试骨架、构建脚本沉淀

## 三、支柱 B：APM 自主闭环

已有能力（7 技能 / 4 子 Agent / 4 命令 / 双端 SDK），
覆盖 **启动 / 渲染 / 白屏 / 内存 / 崩溃**，并遵守五条铁律：

> 无基线不优化 · 单变量 · 必须复测 · 绝不伪造 · 结论带来源

核心承诺：**用户提出需求后，自主完成闭环**。
⚠️ **此承诺尚未被完整验证**（见 `TODO.md` T1）。

## 四、目标仓库结构（草案）

```
mobileAutoAPM/
├── AGENTS.md                    ★ 跨 agent 唯一真源（构建/测试/约定/禁区）
├── CLAUDE.md                    → 一行 `@AGENTS.md`
├── README.md                    ★ 面向移动开发者，三屏内讲清价值
├── ARCHITECTURE.md              ★ 架构与数据流
├── ROADMAP.md                   路线图
├── CHANGELOG.md
├── CONTRIBUTING.md
├── LICENSE
│
├── .github/
│   ├── workflows/               CI：构建 + 测试 + 扫描自检
│   ├── ISSUE_TEMPLATE/
│   └── PULL_REQUEST_TEMPLATE.md
│
├── core/                        ★ 平台内核（与具体 agent 无关）
│   ├── skills/                  能力定义（判断力层）
│   ├── agents/                  子 Agent
│   ├── commands/                用户入口
│   ├── scripts/                 数据平面（确定性工具）
│   └── references/              知识库（方法论 / 选型 / 口径）
│
├── adapters/                    ★ 各 AI code agent 的适配层
│   ├── claude-code/             plugin + marketplace
│   ├── opencode/                .opencode/
│   └── generic/                 AGENTS.md 约定
│
├── runtimes/                    ★ 应用侧埋点 SDK
│   ├── rn-apm/                  React Native
│   └── ios-apm/                 iOS 原生
│
├── evolution/                   ★ 自我进化
│   ├── sources.yaml             知识源清单（可定期拉取）
│   ├── proposals/               Agent 提出的能力更新建议（待人工确认）
│   └── knowledge/               沉淀下来的方案
│
├── tools/
│   └── build-adapters.py        单一真源 → 多 agent 编译
│
└── docs/
    ├── PROGRESS.md
    ├── TODO.md
    ├── RESTRUCTURE-PLAN.md
    ├── diagrams/                架构图 / 原理图 / 流程图
    └── *.md                     各专题文档
```

### 关键设计

| 决策 | 理由 |
|---|---|
| **`core/` 与 `adapters/` 分离** | 能力只写一遍；换 agent 只加适配器。避免"为每个 agent 维护一份"必然产生的漂移 |
| **`AGENTS.md` 为唯一真源** | 跨 agent 事实标准；`CLAUDE.md` 只留一行指向它 |
| **`evolution/` 单列** | 自我进化是一等公民，不是附属脚本 |
| **`runtimes/` 与应用侧 SDK 并列** | 埋点是"装进用户 App 的东西"，与平台自身工具性质不同 |
| **`docs/diagrams/`** | 架构图/原理图集中管理，便于 README 与文档引用 |

## 五、实测基线（重构前后可对比）

用 `ai_readiness.py` 扫出的当前状态：

| 项目 | 类型 | AI 友好度 |
|---|---|---|
| `runtimes/ios-apm`（现 `ios-apm/`） | ios | **72** |
| 参考：真实遗留 iOS 项目 | ios | 68 |
| `runtimes/rn-apm`（现 `rn-apm/`） | react-native | **60** |
| **本仓库根目录** | ios + react-native | **20** ⚠️ |

**本项目自己的 AI 友好度只有 20 分** —— 这是重构要解决的第一个问题，
也是最有说服力的 dogfooding：**平台自己必须先成为它承诺的样子。**

主要缺口：缺 `AGENTS.md`、缺架构文档、缺 CI、缺 lint、README 无可复制命令。

## 六、路线图（草案，待调研定稿）

| 阶段 | 目标 | 出口标准 |
|---|---|---|
| **R0 · 自我达标** | 本仓库自身的 AI 友好度 ≥ 85 | `ai_readiness.py` 扫描通过；CI 绿 |
| **R1 · 定位落地** | README / 架构图 / 路线图 / 文档体系 | 新用户 3 分钟内理解价值并能跑通 |
| **R2 · 支柱 A 成形** | 扫描 → 改造 → 复扫 全流程可用 | 在一个真实遗留项目上跑通并量化提升 |
| **R3 · 核心承诺验证** | 自主闭环演练（`TODO.md` T1） | 无人干预跑完一次完整闭环 |
| **R4 · 自我进化** | 定期更新 skill 与 MCP、沉淀方案 | 机制可运行且有验证门槛 |
| **R5 · 开源运营** | 搜索优化、社区、冷启动 | 目标关键词进入搜索前列 |

⚠️ 顺序有意为之：**先让自己达标，再教别人怎么达标。**
